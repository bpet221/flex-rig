# Where coding work goes: the Code work bar (Mac only)

Each chat in the Claude app on this Mac shows the **Code work bar** above the prompt (the `code-work` mod): **Mac ⟶ Flex Rig**, then Flex Rig's model and effort. This chat always runs here on the Mac; the bar only says where its *coding work* goes. A new chat sends coding work to **Flex Rig**; the user switches with one click or `/code-work mac` / `/code-work flex`. Every message carries a hidden "Code work: …" note with the current choice: follow the latest one. No note (mod not loaded) means Flex Rig. Flex Rig = the user's always-on Windows PC with its own Claude login, driven by the `flex-rig` skill. This file lives only on the Mac (source: `mac/flex-rig-rule.md` in the flex-rig repo), so Flex Rig never hands work to itself.

- **What counts as coding work:** editing files in any repo (code, fixes, refactors, tests, docs, config, scripts: anything that ends in a branch or PR). That includes the sources of this setup if they are in a repo: this rule (`mac/flex-rig-rule.md`), the flex-rig skill and `flexrig.sh` (`skill/`), the Code work bar mod (`code-work/`), `mac/repo-sync.sh` and the install scripts. Those are repo files like any other, so editing them goes wherever the bar says.
- **Code work: Flex Rig:** coding work goes to Flex Rig with the `flex-rig` skill:
  1. `flexrig.sh start --title "<few words>" [--repo NAME] --area <folder the task works in> "full brief"`. It first pushes the user's local edits in that folder (and any commits not on GitHub) to a new branch `mac/<stamp>`, never main, and Flex Rig starts from it, so Flex Rig sees exactly what the user sees. Tell the user its "Pushed: …" line in one line. Repos named in `FLEXRIG_AREA_REPOS` (in `~/.flexrig/config`) always need `--area`. The title shows under the bar while it works ("Flex Rig is working on: …").
     **Model and effort come from the bar:** by default what this chat uses; the user can pick another model or effort in the bar for Flex Rig. The script reads the bar by itself, so pass `--model`/`--effort` only when the user names one in words ("run it on Sonnet over there"). A running session keeps what it started with; changes apply to the next start or follow-up. If Flex Rig can't run that model, finish on the Mac (below), don't silently drop to another model.
  2. **Stay working until Flex Rig is done, with few replies** (the chat must show as working, but a short `wait` loop would be most of the Mac's usage, since every check is a reply that re-sends the whole chat). Run `flexrig.sh wait` in the foreground with the Bash tool's `timeout: 600000`: each call holds the chat "working" for 2.5 minutes with no replies (short, so the user's typed messages don't wait long), then prints one progress line and "STILL WORKING"; run it again right away, with no commentary in between unless something changed that the user should know (a short line at most). Not Monitor, not `run_in_background`. The user steers instantly from the side panel (**View** on the bar); a message they type in the chat arrives at the next check (up to 2.5 min).
  3. **The user's messages while it works** (they show up next to a `wait` result): an instruction about the work goes to Flex Rig at once with `flexrig.sh say "<their words>"`, then tell them "Sent to Flex Rig." in one line and keep waiting. A question for you ("what's it doing?") gets answered here, not forwarded. A message meant for after ("after it's done: …", "queue this") waits: send it with `flexrig.sh followup` once the run is done. If `say` says the run already finished, send it as a follow-up.
  4. **When it's done:** check the PR diff (`gh pr diff <url>`), report in plain words, and send any leftover messages the report lists as a follow-up. Merge with `flexrig.sh merge <id>`: merges the PR, deletes the merged `mac/` branch, fast-forwards the Mac's folder. Then deploy if needed (deploys only from the Mac), and if the PR changed this setup's sources (`code-work/`, `skill/`, `runner/`, `mac/`), run `bash install.sh` from the flex-rig folder on the Mac.
  5. **Messages that arrive after it's done** (the user's queued ones, or a new instruction about the same work) continue the same Flex Rig session: `flexrig.sh followup "<their words>"` (this chat's run is the default), then wait again. If its PR was already merged, Flex Rig starts a new branch and PR by itself.
- **Code work: this Mac:** do the coding work here on the Mac, in a fresh worktree. Don't send it to Flex Rig unless the user asks.
- **Flex Rig offline** (the bar checks every 30 s whether the Mac can reach it; grey dot, "work stays on the Mac"): the note says so. Do the coding work on the Mac in a fresh worktree without trying Flex Rig first, and say "Doing this on the Mac: Flex Rig is offline." in one line. The bar's **Stop** (asks once) stops a running Flex Rig task; **Merge** on a finished one sends a message asking you to run `flexrig.sh merge <id>` and deploy if needed.
- **Only steps that touch the Mac itself stay on the Mac, whatever the bar says:** running an installer that copies into `~/.claude` (e.g. `bash install.sh` from the flex-rig folder after a merge), LaunchAgents and other background jobs, Mac app settings (`~/.claude/settings.json` and other files that live only on the Mac, not in a repo), work in the user's own browser (Chrome and their sign-ins; a coding task that only needs to look at a web page or the app it built still goes to Flex Rig, which has its own hidden test browser), deploys (the deploy logins are only here), anything needing secret keys (`.env`, `.dev.vars` and the like), merging (`flexrig.sh merge`), quick questions and read-only lookups. **Never** read "the Mac's own setup" as covering edits to its sources in a repo: with the bar on Flex Rig, Flex Rig edits the rule, skill, mod, `repo-sync.sh` and installers and opens the PR; the Mac then merges and runs the installer. Never edit the installed copies in `~/.claude` by hand instead. The user's local edits in the area ride along by push-first, so an edit already started in this chat's checkout goes to Flex Rig too. When the Mac has to do one of these steps, it does only that step, not the repo edits around it, and says so in one line ("Doing this on the Mac: it installs into ~/.claude.").
- **Try both machines before asking the user:** if Flex Rig is unreachable, out of usage, or stuck on a missing login, key, tool or permission, finish on the Mac (`flexrig.sh takeover <id>`, or a fresh Mac worktree) and say "Finished on the Mac because Flex Rig was missing X". Ask the user only when both machines are blocked. Never route around a safety check that blocked something on either machine.
- **Mac folders stay current by themselves:** the LaunchAgent `com.flexrig.repo-sync` fast-forwards `main` in every repo under the repos folder (`FLEXRIG_LOCAL_REPOS`) every 10 minutes (`flexrig.sh sync [REPO]` does it now), refreshes the bar's model list, and updates Flex Rig's Claude Code about once a day. It never stashes, resets, commits, switches branches or deletes; if a repo can't update, the user gets one Mac notification per problem.
- Merging and deploying follow the user's usual rules and happen from the Mac.
